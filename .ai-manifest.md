# AI Manifest

This file provides context for AI agents working on this codebase. It describes architectural decisions, boundaries, and constraints.

## Architecture

**Pattern**: Clean Architecture / Hexagonal Architecture (backend only)

**Core Principle**: Business logic (Domain) is isolated from infrastructure (Database, HTTP, external APIs).

**Boundaries**:
- **Domain Layer**: No external dependencies. Pure business logic.
- **Application Layer**: Orchestrates use cases. Depends on Domain only.
- **Infrastructure Layer**: Implements repository interfaces. Depends on Domain.
- **Presentation Layer**: HTTP handlers. Depends on Application.

## Key Decisions

### Why Turborepo + pnpm?
- **Turborepo**: Intelligent task caching and parallelization. Only rebuilds changed packages.
- **pnpm**: Efficient disk usage with symlinked node_modules. Faster installs than npm/yarn.

### Why Next.js 15 + React 19?
- **App Router**: Server Components reduce client-side JavaScript. Faster initial load.
- **React 19**: Improved hydration, better concurrent rendering, forward compatibility.

### Why Zustand + React Query?
- **Zustand**: Minimal boilerplate for local UI state. No provider hell.
- **React Query**: Automatic caching, refetching, and stale data management for server state.
- **Separation**: Local state (Zustand) vs server state (React Query) prevents over-fetching.

### Why Prisma + pg-pool Hybrid?
- **Prisma**: Type-safe ORM for migrations and simple CRUD operations.
- **pg-pool**: Raw SQL for performance-critical queries (e.g., aggregations, complex joins).
- **Why both?**: Developer experience (Prisma) + performance (pg-pool) for specific needs.

### Why MongoDB + PostgreSQL Together?
- **PostgreSQL**: ACID transactions, relational integrity (users, orders, payments).
- **MongoDB**: Flexible schemas for user-generated content, analytics, logs.
- **Hybrid**: Right tool for the job instead of forcing one database for everything.

### Why Node.js Cluster Mode?
- **Horizontal scaling within a single instance**: Utilizes all CPU cores.
- **Automatic recovery**: Workers restart on crash.
- **Development vs Production**: Single worker (dev) for easier debugging, multi-worker (prod) for scale.

### Why Clean Architecture?
Ensures:
1. **Testability**: Business logic testable without database/HTTP.
2. **Flexibility**: Easy to swap PostgreSQL for another database.
3. **Maintainability**: Clear boundaries reduce coupling.

### Why Non-Root Containers?
Security best practice. Reduces attack surface by running as unprivileged user (UID 1000 / node user).

## Monorepo Package Strategy

### Shared Packages

1. **`@repo/eslint-config`**: Centralized linting rules prevent inconsistencies across apps.
2. **`@repo/typescript-config`**: Base, Next.js, and Node.js configurations ensure strict typing.
3. **`@repo/zod-schemas`**: E2E type safety. Frontend and backend share validation schemas.

**Why workspace references?**: Changes to shared packages automatically propagate to consuming apps.

## Extension Points

### Adding a New Use Case

1. **Define domain entity** (if needed) in `apps/api/src/domain/entities/`
2. **Create use case** in `apps/api/src/application/usecases/`
3. **Add HTTP handler** in `apps/api/src/presentation/http/`
4. **Register route** in `apps/api/src/presentation/routes/`
5. **Add Zod schema** (if public API) in `packages/zod-schemas/src/`

### Adding a New Repository

1. **Define interface** in `apps/api/src/domain/repositories/`
2. **Implement** in `apps/api/src/infrastructure/database/postgres/` (or mongodb/)
3. **Inject** into use case via dependency injection in `server.ts`

### Adding Authentication

1. **Create JWT middleware** in `apps/api/src/presentation/middleware/auth.ts`
2. **Add auth use cases** (login, register, refresh) in `apps/api/src/application/usecases/`
3. **Implement user repository** in `apps/api/src/infrastructure/database/postgres/`
4. **Add protected route wrapper** in `apps/api/src/presentation/routes/`

### Adding a New Frontend Page

1. **Create route** in `apps/web/src/app/[route]/page.tsx`
2. **Create components** in `apps/web/src/components/`
3. **Add Zustand store** (if needed) in `apps/web/src/store/`
4. **Add React Query hooks** (if API calls needed) in `apps/web/src/lib/`

## Testing Strategy

### Unit Tests
- **What**: Domain entities, use cases (mocked repositories)
- **Where**: `apps/api/src/**/*.test.ts`
- **Run**: `pnpm --filter api test`

### Integration Tests
- **What**: Infrastructure adapters with real databases (Testcontainers)
- **Where**: `apps/api/tests/integration/`
- **Run**: `pnpm --filter api test:integration` (add script)

### E2E Tests
- **What**: HTTP endpoints with real database
- **Where**: `apps/api/tests/e2e/`
- **Run**: `pnpm --filter api test:e2e` (add script)

### Frontend Tests
- **What**: Component behavior, user interactions
- **Where**: `apps/web/src/**/*.test.tsx`
- **Run**: `pnpm --filter web test` (configure Jest)

## Constraints

### ❌ Do NOT Do This

- **Do NOT add business logic to HTTP handlers**: Keep them thin (validation → call use case → return response).
- **Do NOT let Domain layer depend on Infrastructure**: No importing database packages in domain entities.
- **Do NOT store secrets in code or `.env`**: Use secret management in production (e.g., Kubernetes secrets, AWS Secrets Manager).
- **Do NOT skip security checks**: Always run `make secure` before committing.
- **Do NOT bypass rate limiting in production**: Even for internal tools.

### ✅ DO This

- **DO write tests for all use cases**: Aim for >80% coverage in domain/application layers.
- **DO use dependency injection for repositories**: Pass repositories to use cases in constructors.
- **DO validate all inputs with Zod**: Never trust user input.
- **DO use Prisma migrations**: Never manually alter database schema.
- **DO use pg-pool for complex queries**: Don't force Prisma for everything.

## Deployment

### Frontend (Vercel Recommended)

1. Connect GitHub repository to Vercel
2. Set build command: `pnpm turbo run build --filter=web`
3. Set environment variables:
   - `NEXT_PUBLIC_API_URL`: Backend API URL

### Backend (Render / Railway Recommended)

1. Deploy as Docker container using `apps/api/Dockerfile`
2. Set environment variables:
   - `DATABASE_URL`: PostgreSQL connection string
   - `MONGODB_URL`: MongoDB connection string
   - `REDIS_URL`: Redis connection string
   - `CORS_ORIGINS`: Comma-separated frontend URLs
   - `NODE_ENV=production`

### Database

- **PostgreSQL**: Railway / Supabase / AWS RDS
- **MongoDB**: MongoDB Atlas
- **Redis**: Upstash / Redis Labs

### Health Checks

- **Liveness**: `GET /health`
- **Readiness**: `GET /ready` (checks DB connections)

Configure load balancers to use `/ready` for routing decisions.

## Configuration

All configuration is via environment variables (12-factor app methodology).

**Local Development**: Copy `.env.example` to `.env`  
**Production**: Inject via orchestration platform (Kubernetes secrets, Render environment variables)
